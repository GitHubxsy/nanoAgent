08. 上下文窗口：模型的“工作记忆”有多大

上下文窗口决定模型一次能看到多少 token；窗口越长，位置编码、Attention 计算和 KV Cache 压力越大。

ContextPositionKV Cache
从场景开始 直接看演示

Scenario

为什么需要这一讲

为什么模型不能无限记住所有对话？因为每次推理都要把上下文作为输入处理，长度越大，计算和显存压力越明显。

Mental Model

先建立一个直觉

上下文窗口像工作台：东西可以放很多，但工作台越大，找东西、移动东西、维护现场的成本也越高。

KV Cache 随上下文增长

上下文越长，缓存的 K/V 越多，显存占用会线性增长。

看 GitHub 行号

 176 print("实验 5：不同上下文长度的 KV Cache 显存需求")

 179 def kv_cache_size_mb(n_tokens, n_layers, n_heads, head_dim, dtype_bytes=2):
 180     """计算 KV Cache 的显存占用（MB）"""
 181     return n_tokens * n_layers * n_heads * head_dim * 2 * dtype_bytes / (1024 * 1024)
 182
 183 # 不同模型配置
 184 configs = [
 185     ("GPT-2",       12, 12,  64, 2),
 186     ("LLaMA 7B",    32, 32, 128, 2),
 187     ("LLaMA 70B",   80, 64, 128, 2),
 188 ]
 189
 190 context_lengths = [1024, 4096, 32768, 131072, 1000000]
 191
 192 print(f"\n  KV Cache 显存（float16）:")
 193 print(f"\n  {'模型':<14}", end="")
 194 for ctx in context_lengths:
 195     if ctx >= 1000000:
 196         label = f"{ctx//1000000}M"
 197     elif ctx >= 1024:
 198         label = f"{ctx//1024}K"
 199     else:
 200         label = str(ctx)
 201     print(f"  {label:>8}", end="")
 202 print()
 203 print("  " + "-" * (14 + len(context_lengths) * 10))
 204
 205 for name, layers, heads, head_dim, dtype in configs:
 206     print(f"  {name:<14}", end="")
 207     for ctx in context_lengths:
 208         size_mb = kv_cache_size_mb(ctx, layers, heads, head_dim, dtype)
 209         if size_mb >= 1024:
 210             print(f"  {size_mb/1024:>6.1f}GB", end="")
 211         else:
 212             print(f"  {size_mb:>6.0f}MB", end="")
 213     print()
 214

 216   → 上下文长度和 KV Cache 显存成正比
 217   → LLaMA 7B 在 128K 上下文时，KV Cache 就要约 64 GB

Takeaway

这一讲看懂什么

  • 上下文窗口是模型一次推理能看到的 token 上限。
  • 长上下文不是免费能力，会带来计算、显存和检索质量问题。
  • Agent 的记忆、压缩、检索都在处理上下文窗口的现实边界。

Key Points

讲解要点

  • 能装下不代表能用好，长上下文也会稀释注意力。
  • 位置编码告诉模型 token 在哪里。
  • KV Cache 让长上下文的成本从抽象限制变成具体显存占用。

Pitfalls

容易误解

  • 不要把上下文窗口等同于长期记忆，窗口外的信息模型看不到。
  • 更长窗口不自动等于更高准确率。
  • 截断上下文时，最容易丢掉早期但关键的信息。
