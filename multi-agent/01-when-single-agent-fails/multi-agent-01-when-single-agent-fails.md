## 开场：先别急着搭多 Agent

打开 X，每天都有人发新的多 Agent 框架——CrewAI、AutoGen、LangGraph、Swarm——配图都长得差不多：圆圈、箭头、几个小机器人围在一起开会。看起来很美。

然后你想跟一下，开始做自己的多 Agent 系统。第一个问题就把你卡住了：

> **我这个任务，到底需不需要多 Agent？**

去 Twitter 上问，会得到两个相反的答案：

- 一派人说："2026 年了还在用单 Agent？多 Agent 是必然趋势。"
- 另一派人说："Anthropic 自己都发了《Don't Build Multi-Agents》，老老实实写好 prompt 比啥都强。"

两边都举得出例子。你看完更迷糊了。

这个系列从这个问题开始。**不预设结论**——我们先认认真真做一个单 Agent baseline，让它在一个真实任务上崩给我们看；然后下一章再开始拆多 Agent，每加一步都要回答"这一步换来了什么"。

第七章再回头算账，看哪些步是真的赚了。

## 一、本系列的 demo：自动化技术调研助手

整个系列围绕一个具体场景：**输入一个技术问题，输出一份研究报告**。

具体一点：

> **输入**：「对比一下 2025-2026 年主流的 GPU 推理优化方案——FlashAttention、PagedAttention、SGLang、vLLM、TensorRT-LLM——哪个适合长上下文场景？」
>
> **期望输出**：一份 ~3000 字的对比报告，覆盖各方案的核心思路、适用场景、性能数据、社区生态，最后给出推荐。

选这个任务的理由：

1. **够大，单 Agent 不一定装得下**——5 个方案 × 4 个维度，潜在引用论文和博客几十篇
2. **有并行结构**——5 个方案可以同时调研
3. **有视角多样性的需求**——光"调研"不够，还需要"批判"和"整合"
4. **失败模式真实**——容易出现引用过时、信息冲突、漏掉关键方案、报告头重脚轻

接下来 7 章，我们就围绕这个 demo，从单 Agent baseline 开始，慢慢把它做成一个 7 章后能稳定交付报告的多 Agent 系统。

## 二、单 Agent baseline：先用最简单的方式做一遍

在拆多 Agent 之前，**先用最简单的方式跑一遍**——这是这个系列和市面上多 Agent 教程的最大差别。

我们直接复用 [Agent 系列第 03 章](../../agent/03-skills-mcp/) 的实现，加两个工具：

```python
# 单 Agent 配置
tools = [
    web_search,    # 调用搜索引擎，返回前 N 个结果摘要
    web_read,      # 抓取一个 URL 的正文，返回 Markdown
    write_file,    # 把报告写到磁盘
]

system_prompt = """
你是一个技术调研助手。用户会给你一个技术问题，
你需要：
1. 通过 web_search 找到相关资料
2. 用 web_read 读取关键文章的正文
3. 综合信息，写一份对比报告
4. 用 write_file 保存到 report.md
"""
```

代码量很小，就这样。模型用 Claude Sonnet 4.6 / GPT-4o / DeepSeek-V3 都行，不挑。

跑一次，看它输出什么。

## 三、跑一次，看它在哪里崩

把上面那个 GPU 推理优化的问题丢给它，观察它的循环：

```text
[Round 1] web_search("FlashAttention long context inference")
  → 返回 10 条结果，每条带标题、URL、摘要 (~3K tokens)
[Round 2] web_search("PagedAttention vLLM benchmark")
  → 返回 10 条结果 (~3K tokens)
[Round 3] web_search("SGLang vs vLLM 2025")
  → 返回 10 条结果 (~3K tokens)
[Round 4] web_read("https://...flashattention-3-paper")
  → 论文正文 ~25K tokens
[Round 5] web_read("https://...pagedattention-blog")
  → 博客正文 ~8K tokens
[Round 6] web_read("https://...sglang-doc")
  → 文档 ~12K tokens
...
[Round 12] 上下文已用 ~120K，准备写报告
[Round 13] write_file("report.md", "...")
  → 输出一份 2000 字的报告
```

报告写出来了。但仔细看，问题就开始浮现。

### 翻车点 1：Context 爆炸

到 Round 12 时上下文已经用了 120K tokens——其中 90% 是搜索结果摘要和文章正文。模型最后写报告时，**早期读到的内容已经被注意力稀释**，写出来的内容偏向最后读到的几篇。

具体表现：报告里 PagedAttention 部分写得最详细（因为最后读的），FlashAttention 部分明显单薄，TensorRT-LLM 几乎一笔带过。

### 翻车点 2：串行慢

5 个方案，模型一个一个搜——`FlashAttention` 搜完搜 `PagedAttention`，搜完再搜 `SGLang`。每次搜索 + 读取 ~3 分钟，5 个方案 × 3 维度 = 15 次循环，**总耗时 30+ 分钟**。

而这些搜索之间没有依赖关系——FlashAttention 怎么样和 PagedAttention 怎么样是两件独立的事，**完全可以并行**。但单 Agent 架构里，"并行"对模型来说不存在——它只能一次发一个工具调用。

### 翻车点 3：视角单一

报告里有这么一句：

> "FlashAttention 在长上下文场景下性能最好，比 PagedAttention 快 2.3 倍。"

这句话从某篇博客抄来的——但那篇博客是 FlashAttention 团队 2024 年发的。实际上 PagedAttention 后续的 v2 已经追上了大部分场景。

模型没有"批判"这一步。它把读到的内容直接整合，没人质疑信息的可信度、时效性、立场偏差。

更糟的是另一篇文章里说 "PagedAttention 比 FlashAttention 快 1.8 倍"——**两篇文章观点对立，模型同时引用，没察觉到冲突**。

### 翻车点 4：任务边界乱

整个 system prompt 把"搜索"、"阅读"、"对比"、"判断"、"写作"五件事混在一起。模型每一轮都在切换——这一轮在搜索，下一轮在读，下一轮在判断要不要再搜，下一轮开始写报告……

切换的代价是：

- 注意力分散，每一项都做不深
- 出错了不知道是哪一步出的（搜得不全？读漏了？整合错了？）
- 加新功能（比如"加一个 critic"）会让 prompt 进一步膨胀

## 四、这是工具问题、prompt 问题，还是架构问题？

到这里，一个公允的反问是：

> "这些问题真的是单 Agent 的问题吗？换个更厉害的搜索工具、写个更好的 prompt，是不是就解决了？"

值得认真回答这个问题，因为**很多看起来"需要多 Agent"的场景，本质上是工具或 prompt 没设计好**。

### 翻车点 1（context 爆炸）：能靠工具/prompt 解决吗？

**部分可以**。把 web_search 的结果做摘要、把 web_read 的内容做摘要，能让 context 占用降下来。Claude Code 里的 `Read` 默认带行号分页就是这个思路。

但根本解不掉——只要任务规模继续涨（10 个方案、20 个方案），单 Agent 的 context 总会被填满。

### 翻车点 2（串行慢）：能靠工具/prompt 解决吗？

**几乎不行**。单 Agent 的循环本身就是串行的——一次一个工具调用，等结果回来再决定下一步。你可以让它一次工具调用里塞 5 个搜索（OpenAI 的 parallel tool calls 就是这个），但只对**完全独立**的调用有效，**结果回来后还是要在同一个 context 里串行处理**。

### 翻车点 3（视角单一）：能靠工具/prompt 解决吗？

**勉强可以，但代价大**。你可以在 prompt 里加 "在写报告前，先批判一下你收集到的每条信息"。它会装模作样地批判一下，但效果有限——**因为是同一个模型在同一个 context 里"自我批判"，它已经被自己读到的内容洗脑了**。

让一个独立的 critic（不知道前面发生了什么）来批判，效果完全不同。但那已经是多 Agent 了。

### 翻车点 4（任务边界乱）：能靠工具/prompt 解决吗？

**能改善，不能根治**。把 system prompt 写得很结构化，"先搜索，搜够了再读，读够了再写"——能减轻问题。但模型不会严格遵守，它会"在写到一半时发现遗漏，然后回去搜"，这本来是好事，但它的 context 已经塞了 80K 内容了。

---

总结一下这四个翻车点的"是工具/prompt 问题还是架构问题"：

| 翻车点 | 工具/prompt 能解吗 | 多 Agent 能解吗 |
|--------|-------------------|----------------|
| Context 爆炸 | 部分能 | 能（每个 Agent 独立 context） |
| 串行慢 | 几乎不能 | 能（worker 并行） |
| 视角单一 | 勉强能 | 能（独立的 critic） |
| 任务边界乱 | 能改善不能根治 | 能（每个 Agent 单一职责） |

**结论很清楚**：4 个翻车点里，2 个是真正的架构问题（context 爆炸 + 串行慢），1 个 prompt 解不彻底（视角单一），1 个 prompt 能改善但不优雅（任务边界）。

这是判断"该不该上多 Agent"的核心标准——**问题是不是真的来自架构，而不是工程惰性**。

## 五、多 Agent 能解什么、解不了什么

在我们兴奋地开始拆多 Agent 之前，先打个预防针：**多 Agent 不是免费的**。它会带来一组新的问题：

- **通信成本**：Agent 之间传数据要花 token
- **状态一致性**：3 个 worker 都搜了同一篇论文怎么办
- **错误传播**：一个 worker 跑挂了，整个系统怎么办
- **调试地狱**：5 个 Agent 各跑各的，出问题了去哪查

这些问题会让多 Agent 系统**比单 Agent 系统贵 3-5 倍 token**，而且更难调试。

所以正确的姿势是：**只在多 Agent 真正赢的场景用它**。

经验上，多 Agent 真的赢需要三个条件**同时**满足：

1. **任务可并行**：子任务之间没有依赖，能真的同时跑
2. **视角需要多样**：单视角的输出不够好，需要不同立场的 Agent 互相校验
3. **上下文需要隔离**：每个子任务的上下文都很大，塞在一起会爆

只满足一个的，多半是 prompt 没写好；满足两个的，可以试试单 Agent + SubAgent（临时帮手）；三个都满足的，才真的需要常驻多 Agent 团队。

GPU 推理优化调研这个 demo，三个条件都满足：

1. ✅ 5 个方案并行可调研
2. ✅ 需要 critic 视角避免引用过时
3. ✅ 每个方案的资料加起来都几十 K，5 个方案塞一起必爆

**所以这个 demo 真的值得用多 Agent**。这也是它能成为一个"诚实的"系列 demo 的原因——不是为了演示多 Agent 而生造场景。

---

## 一句话总结

多 Agent 不是"更高级的单 Agent"，而是**对一类特殊场景的针对性设计**。

判断标准是看你的场景是否同时满足"可并行 + 多视角 + 上下文需隔离"三个条件——只满足一个的，老老实实写好 prompt；两个的，加个 SubAgent；三个的，才需要常驻多 Agent 团队。

## 下一篇预告

这一章我们用单 Agent 做了 baseline，看到了它在四个地方系统性翻车。下一篇就开始拆多 Agent——但不是把所有问题一次性都解决，而是**先做最克制的第一刀**：

> 1 个 Planner（拆解问题）+ N 个 Searcher（并行搜）+ 1 个 Writer（整合输出）

这个最小骨架先把"context 爆炸"和"串行慢"两个最硬的问题解掉，留下"视角单一"和"任务边界"给后面的章节。

写之前要先回答一个绕不开的问题：**第一刀该怎么切？** 是按"职责"切（搜索者、阅读者、写作者），还是按"上下文边界"切（每个 worker 占独立的 context）？这两种切法看起来差不多，结果差很远。第二章会摆出来对比讲清楚。
